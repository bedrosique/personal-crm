# Личная CRM

Идея и ограничения: [описание проекта](specs/01-продуктовая-идея.md).

## Локальная база данных

Нужен запущенный Docker Desktop с Linux-контейнерами и Docker Compose.
В Docker работает только PostgreSQL; приложение будет запускаться отдельно.

Настройки подключения находятся в `.env`. Этот файл исключён из Git.
`.env.example` содержит только названия переменных, без значений.

Если `.env` ещё нет, создайте его по образцу `.env.example`:

- `POSTGRES_DB` — имя базы, например `personal_crm`.
- `POSTGRES_USER` — пользователь базы, например `personal_crm`.
- `POSTGRES_PASSWORD` — длинный случайный пароль. Для простого составления адреса используйте буквы и цифры.
- `DATABASE_URL` — строка вида `postgresql://<user>:<password>@127.0.0.1:5432/<database>`. Подставьте те же значения. Если в пароле есть специальные символы, закодируйте их для URL.

Не отправляйте содержимое `.env` в переписку и не добавляйте его в Git.
Строка подключения предназначена только для серверного кода; не используйте префикс `NEXT_PUBLIC_`.

Запуск из папки проекта:

```powershell
docker compose up -d --wait
```

Проверка состояния:

```powershell
docker compose ps
```

У сервиса `postgres` должно быть состояние `healthy`. База доступна только с этого компьютера: `127.0.0.1:5432`.

Проверка подключения по TCP с паролем, без его вывода:

```powershell
docker compose exec -T postgres sh -c 'export PGPASSWORD=$POSTGRES_PASSWORD; echo SELECT 1 | psql -h 127.0.0.1 -U $POSTGRES_USER -d $POSTGRES_DB -v ON_ERROR_STOP=1'
```

В ответ должна появиться строка со значением `1`. Пароль берётся из окружения контейнера.

Остановка с сохранением данных:

```powershell
docker compose stop
```

Данные хранятся в отдельном Docker volume `personal-crm_postgres_data` и сохраняются при перезапуске и пересоздании контейнера.
Не выполняйте `docker compose down -v`: это удаляет данные.
Изменение пароля в `.env` не меняет пароль уже созданной базы.

Не запускайте `docker compose config` без `--quiet` и не публикуйте `docker inspect`: эти команды могут показать секреты.

Если PowerShell не находит `docker`, добавьте CLI в PATH текущего окна:

```powershell
$env:Path = "$env:LOCALAPPDATA\Programs\DockerDesktop\resources\bin;$env:Path"
```

Приложение, схема Drizzle и миграции находятся в этом проекте. Инструкции по запуску прототипа приведены ниже.

## Запуск прототипа

Приложение использует Next.js, React, TypeScript, Tailwind CSS, компоненты по подходу shadcn/ui и Drizzle. Доступ к PostgreSQL выполняется только на сервере.

После настройки `.env` и запуска существующей PostgreSQL:

```powershell
pnpm install
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Откройте http://127.0.0.1:3000. Для готовой сборки: `pnpm build`, затем `pnpm start`.

Если команды не находятся в PowerShell, добавьте установленные Node.js и pnpm в PATH текущего окна:

```powershell
$env:Path = "C:\Program Files\nodejs;$env:APPDATA\npm;$env:Path"
```

## Проверка руками

1. На главной странице отображаются контакты. Введите часть имени, например «Пушкин», и нажмите «Найти».
2. Откройте карточку, измените заметку и нажмите «Сохранить контакт». Обновите страницу — заметка сохранится.
3. Нажмите «Добавить контакт», укажите имя и сохраните. Найдите новый контакт по имени.
4. Откройте тот же адрес в другом браузере — контакты и заметки будут те же.
5. У части писателей нет телефона или почты: в списке показано тире, в карточке поле пустое.

## Тестовые писатели и источники

`data/writers.json` содержит зафиксированный набор 1000 уникальных писателей. Источник биографий — Wikidata (CC0). Отбор: люди с профессией поэта, романиста, детского писателя или драматурга, известным литературным произведением и местом рождения; приоритет — количество языковых разделов Wikimedia. Это воспроизводимая учебная подборка, а не объективный рейтинг величия. Имена используются в форме, указанной в Wikidata; возможны литературные псевдонимы и традиционные имена древних авторов.

Биография хранится в заметках: дата рождения с точностью источника, одно известное произведение и/или факт о месте рождения. В карточках остаются только биографические сведения. Источники сохранены в материалах генерации: `data/writers.json` (Wikidata ID автора, произведения и места рождения), `data/writer-seed-v1.json` (исходные записи со ссылками), `data/writer-localization.json` (русские подписи и статьи), `data/writer-title-reviews.json` (проверенные русские названия с подтверждениями и номерами версий статей), `data/writer-russian-labels.json` (подписи для генератора). Неоднозначные даты исключены из отбора; известный только год не выдаётся за точный день. Даты из SPARQL представлены в григорианском календаре; точность сохранена, а годы до нашей эры преобразованы из астрономической нумерации. Подробнее: https://www.wikidata.org/wiki/Help:Dates.

Заполненность биографии: 300 карточек с одним сведением, 400 с двумя, 300 со всеми тремя. Контакты: 300 с телефоном и email, 200 только с телефоном, 200 только с email, 300 без обоих полей. Порядок распределений независимый и детерминированный.

Все телефоны и email вымышлены. Email уникальны и используют `example.com`. Телефоны уникальны, используют коды 212, 213, 312, 415, 617, 202, 206, 305, 404, 503 и только диапазон 555-0100–555-0199, зарезервированный NANPA: https://nanpa.com/numbering/555-line-numbers.

`pnpm db:seed` работает без сети и повторно не создаёт дубликаты. Идентификатор карточки детерминированно получен из Wikidata ID. Существующие карточки, включая пользовательские правки, не перезаписываются и не удаляются. Поэтому после ручного изменения заполненности проверка исходных пропорций может перестать проходить — это ожидаемо.

`pnpm data:fetch` заново получает данные из Wikidata, разрешает подписи и проверяет точность дат. Требует интернета; запросы могут ограничиваться источником. Зафиксированный набор уже включён в проект, повторная загрузка для запуска не нужна. Промежуточные результаты сохраняются для проверки происхождения данных.

## Автоматические проверки

```powershell
pnpm typecheck
pnpm build
pnpm verify
pnpm exec playwright install chromium firefox
pnpm test:e2e
```

Последняя команда требует запущенного приложения на порту 3000. Она проверяет интерфейс в Chromium и Firefox, сохранение в PostgreSQL, открытие после закрытия страницы и мобильную ширину. Снимки сохраняются в `artifacts/`. Проверка добавления оставляет явно помеченный тестовый контакт, чтобы не удалять данные без разрешения. Каждый запуск проверки добавления оставляет один проверочный контакт; `pnpm verify` считает только 1000 карточек писателей и не затрагивает остальные контакты.

## Очистка заметок писателей

`pnpm data:clean:preview` показывает план без изменения базы. `pnpm data:clean` обновляет только карточки, полностью совпадающие с исходным генератором; уже очищенные карточки повторно не меняются. Если заметка, имя, телефон или email отличаются, вся карточка пропускается. Другие контакты не затрагиваются.

Перед записью скрипт блокирует строки на время транзакции и сохраняет резервную копию всех контактов в `artifacts/backups/writers-cleanup-<дата>.json`. Копия содержит личные данные, исключена из Git и предназначена для локального хранения. При ошибке проверки транзакция отменяется. Телефоны, email и набор биографических полей не меняются.

Подтверждённые русские названия хранятся отдельно от исходных данных; автоматический перевод не используется. `pnpm data:localize` обновляет материалы для сверки, `node scripts/prepare-writer-localization.mjs` собирает проверенные подписи. Новые названия, найденные в библиографиях, перед включением проверяются по оригиналу. Если подтверждения русского варианта нет, сохраняется исходное написание.

## Сохранение изменений в GitHub

После подключения репозитория сохраняйте готовые изменения из папки проекта:

```powershell
git status
git add .
git diff --cached --stat
git commit -m "Update personal CRM"
git push
```

Перед коммитом проверьте список файлов. `.env`, локальная база PostgreSQL, резервные копии, пользовательские заметки из базы, журналы Codex и `node_modules` не публикуются. На GitHub сохраняются код, миграции и воспроизводимые тестовые данные. Локальную базу нужно резервировать отдельно. Для другого изменения замените текст коммита на короткое описание по-английски.

## Защита сохранения в нескольких вкладках

Карточка передаёт серверу версию `updated_at`, с которой она была открыта. Сервер одним запросом PostgreSQL проверяет ID и версию и сохраняет изменения только при совпадении. Версия хранится с полной точностью до микросекунд и увеличивается при каждом успешном сохранении. Проверка не отделена от записи, поэтому два почти одновременных запроса со старой версией не могут оба успешно сохранить данные. Схема базы и миграции не менялись.

При конфликте появляется сообщение: контакт уже изменён в другой вкладке. Все введённые поля остаются в форме. Скопируйте свой текст, откройте ту же карточку в новой вкладке, сравните изменения и перенесите нужное вручную. Повторное нажатие «Сохранить» в устаревшей вкладке не перезаписывает свежую запись. Не обновляйте страницу с несохранённым текстом до копирования: черновик хранится в открытой форме, не на диске.

Проверка руками: откройте один контакт в двух вкладках, в каждой измените заметку и сохраните первую вкладку. Сохранение второй должно показать конфликт и сохранить её текст в поле. В новой вкладке должна отображаться версия из первой вкладки.

Безопасный автоматический тест:

```powershell
pnpm build
pnpm test:concurrency
```

Тест требует работающую PostgreSQL и установленный Chromium (`pnpm exec playwright install chromium`). Он создаёт отдельную временную базу `crm_concurrency_test_<случайный суффикс>` в том же локальном PostgreSQL; для этого у пользователя базы должно быть право создания баз. Миграции применяются только к временной базе. Отдельный Next.js-процесс запускается на свободном локальном порту с подключением к этой базе. После теста удаляется только созданная этим запуском временная база. Существующая база используется только для проверки контрольной суммы всех контактов до и после теста. Seed не запускается.

Сценарии: две вкладки и сохранность всех полей черновика, повторная попытка устаревшего сохранения, ручной перенос в актуальную карточку, два одновременно выпущенных POST-запроса, дальнейшие сохранения победившей вкладки, отсутствие версии, смена версии в пределах одной миллисекунды и создание нового контакта.
